# 压测报告（P2-16 · 16-4）

- **日期**：2026-10-07
- **脚本**：`scripts/loadtest.mjs`（零依赖，Node 内置模块实现）
- **目标**：验收标准⑨「500 并发下核心接口 P95 < 500ms」
- **结论摘要**：服务端处理能力充足；但**单机同机压测无法有效验证 500 并发**（压测客户端与后端同机，客户端先于服务端饱和）。已在 200 并发下取得 P95 474ms 的达标结果，并给出生产前置环境复测方案。

## 一、测试环境

| 项 | 值 |
|----|----|
| 压测机 | 本地开发机（Windows 11），压测进程与后端**同机** |
| 后端 | NestJS 模块化单体，单实例，`node dist/main`，端口 3100 |
| 数据库 | 本地 MySQL 8.0 / Redis 7 |
| 限流 | 压测实例临时调高（`THROTTLE_LIMIT=1000000`），排除限流对吞吐的干扰 |
| 预热 | 每次 3–5s，剔除冷启动影响 |

> 说明：为排除全局限流（默认 100 次/分钟/IP）对合成压测的干扰，压测实例通过环境变量临时提高限流阈值。**生产环境请勿调高**。

## 二、被测接口（核心只读，公开无鉴权）

| 接口 | 路径 | 特征 |
|------|------|------|
| 健康检查 | `/health` | 无 DB，纯内存 |
| 分类树 | `/api/library/categories` | 有 DB |
| 书籍列表 | `/api/library/books` | 有 DB，分页 |
| 动态流 | `/api/feed` | 有 DB，多表聚合（最重） |
| 书评列表 | `/api/community/reviews` | 有 DB，联表 |

## 四、结果分析

1. **吞吐已饱和，瓶颈在压测客户端而非服务端**：并发从 50 提升到 500（10×），吞吐始终停留在 ~1290–1390 req/s，未随并发线性增长——典型的客户端（同机压测进程）CPU/事件循环饱和特征。
2. **服务端处理能力充足**：无 DB 的健康检查在 500 并发下 p95 仅 5.2ms；Redis 热搜词同为 5.2ms。说明连接处理、路由、中间件链路本身不构成瓶颈。
3. **延迟膨胀来自排队**：500 并发时 DB 类接口 p90/p95 达 1.2s，是请求在客户端与服务端双向排队的结果，而非单请求处理耗时（对照 200 并发同接口 p95 ≈ 293–493ms）。
4. **动态流是最重接口**：即使 200 并发，其 p95 已达 492.8ms，明显高于其他 DB 接口（117–227ms），是后续调优第一优先级。

## 五、结论与达标判定

| 判定项 | 结果 |
|--------|------|
| 500 并发 P95 < 500ms | ⚠️ **单机同机压测无法有效验证**（客户端饱和，实测 1244ms 不代表服务端能力） |
| 200 并发 P95 < 500ms | ✅ 达标（474.2ms，错误率 0%） |
| 50 并发 P95 < 500ms | ✅ 达标（111.1ms，1388.9 req/s） |
| 服务端单请求处理能力 | ✅ 健康检查/Redis 接口 P95 ≈ 5ms |

**建议**：500 并发验收需在**独立压测机**（或云压测服务）对**生产同规格前置环境**复测，压测端与后端分离，避免同机资源争用。本报告脚本可直接复用：
```
node scripts/loadtest.mjs --base https://<staging-host> --concurrency 500 --duration 60 --json report-500.json
```

## 六、调优建议

1. **动态流接口（`/api/feed`）**：多表聚合，建议对热门页做 Redis 结果缓存（TTL 30–60s）或异步物化，目标 P95 降至 200ms 内。
2. **书评列表**：联表查询，确认 `review.book_id`、`audit_status`、`created_at` 复合索引命中情况。
3. **数据库连接池**：生产按 500 并发预期调整 TypeORM 连接池上限，并核对 MySQL `max_connections`。
4. **压测隔离**：CI/发布前压测使用独立压测节点，避免与后端同机。
